# 두 축 검토

`HEAD`와 고정 시점 사이의 변경을 검토한다.
- **기준**: 이 저장소의 문서화된 규칙과 계약을 지키는가?
- **요구**: 원래 spec·계획 항목·사용자 요청을 그대로 구현했는가?

두 축은 서로 오염되지 않도록 **병렬 하위 에이전트**로 각각 새 컨텍스트에서 돌리고, 결과를 모은다. 하위 에이전트는 읽기 전용 검토자 `knol-reviewer`(`.kiro/agents/knol-reviewer.md`)를 쓴다. 목록에 없으면 `general-task-execution`에 "파일을 고치지 말 것"을 붙여 쓴다.

## 1. 고정 시점
사용자가 말한 시점(SHA, 브랜치, `main`, `HEAD~3`)을 쓴다. 말하지 않았으면 묻는다. `git rev-parse <시점>`으로 확인하고 diff가 비지 않았는지 본다. 잘못된 ref나 빈 diff는 여기서 끝낸다.

diff 명령을 정한다.
- 커밋된 변경: `git diff <시점>...HEAD`와 `git log <시점>..HEAD --oneline`.
- 미커밋 작업을 검토할 때: `git diff <시점>` (작업 트리 포함)과 새 파일 목록. 이 세션이 만들지 않은 파일은 사용자가 포함하라고 한 경우에만 넣는다.

## 2. 요구 출처
순서대로 찾는다: 커밋 메시지나 사용자가 준 경로, 브랜치·주제에 맞는 `.kiro/specs/*/`, 계획 문서의 해당 작업 행과 STATUS 항목, 이 대화의 사용자 요청. 없으면 사용자에게 묻고, 없다고 하면 요구 축은 "요구 출처 없음"으로 보고한다.

## 3. 기준 출처
이 저장소에서 코드 작성 규칙을 담은 파일을 모은다. 최소한:
- `AGENTS.md`의 구조와 금지 규칙, 변경 파일 경로에 맞는 영역 절차(`.agents/skills/*/SKILL.md`).
- 관련 ADR(`docs/decisions/`), 계약 문서(저장 계약, 양식, 점수, 소리), UI 변경이면 `DESIGN.md`의 관련 절.
- 제품 용어 사용 기준(화면 문구·접근성 이름이 바뀌었으면).
- 도구가 강제하는 것(ESLint 설정, tsconfig strict, `pnpm docs:check`)은 건너뛴다.
- 저장소 기준이 정하지 않은 곳에는 기본 냄새 목록 [references/smells.md](references/smells.md)를 적용한다. 저장소 기준이 항상 우선하고, 냄새는 판단 사항이다.

## 4. 하위 에이전트 두 개를 함께 실행
둘을 같은 차례에 띄우고 보고를 기다린다. 하위 에이전트는 이 대화를 모르므로 필요한 것을 브리프에 모두 넣는다.

**기준 에이전트 브리프**: diff 명령과 커밋 목록, 3단계의 기준 파일 목록, `references/smells.md`의 경로, 그리고 이 지시. "파일·hunk별로 (a) 문서화된 기준을 어긴 곳: 기준 파일과 규칙을 인용, (b) 눈에 띄는 기본 냄새: 이름과 hunk 인용. 문서 기준 위반은 확정일 수 있지만 냄새는 늘 판단 사항이다. 저장소 기준이 냄새 목록보다 우선한다. 도구가 강제하는 것은 건너뛴다. 400단어 이내, 한국어."

**요구 에이전트 브리프**: diff 명령과 커밋 목록, 요구 출처의 경로나 내용, 그리고 이 지시. "(a) 요구했는데 없거나 일부만 된 것, (b) 요구하지 않았는데 diff에 있는 동작(범위 초과), (c) 구현된 것 같지만 틀려 보이는 것. 각 항목에 요구 문장을 인용한다. 400단어 이내, 한국어."

요구 출처가 없으면 요구 에이전트를 띄우지 않고 보고에 적는다.

## 5. 모으기
`## 기준`과 `## 요구` 제목 아래 두 보고를 거의 그대로 둔다. 두 축을 합치거나 순위를 다시 매기지 않는다. 한 축의 통과가 다른 축의 실패를 가리지 않게 하려고 나눈 것이다.

끝에 한 줄: 축별 발견 수와 각 축 안에서 가장 심각한 문제. 두 축을 통틀어 하나를 고르지 않는다.
