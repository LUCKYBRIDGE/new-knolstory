# 회고: 환경 고치기

코드가 아니라 에이전트가 일하는 **환경**을 고쳐 다음 실행을 낫게 만든다.

## 1. 원자료 읽기
사용자가 정한 세션을 읽는다. 정하지 않았으면 지금 세션이다. 실행한 명령, 실패, 되돌아간 지점, 오래 찾은 정보, 사용자가 바로잡은 곳을 본다. 하네스 작성 기준(`kiro-writing`)을 따른다.

## 2. 후보 찾기
| 분류 | 찾는 것 | 쓸 때 |
|---|---|---|
| 길 찾기 | 맞는 파일을 찾기 어려웠나, 숨은 파일 의존이 있나. 스티어링의 경로 안내나 `fileMatchPattern`이 있었으면 빨랐나 | 정보를 찾는 데 오래 걸렸을 때 |
| 자동 검사 | 에이전트의 실수를 검사로 잡을 수 있었나. 이미 있는 검사(`package.json` 스크립트, `.github/workflows/ci.yml`, `.kiro/scripts/check-kiro.mjs`)가 연결되지 않았거나 조용히 깨진 것이 먼저다. 새로 만들지 말고 그것부터 | 검사로 잡을 수 있는 실수를 했을 때 |
| 규칙 | 기계적 위반(정해진 문법, 금지 API, 파일 위치)은 결정적 검사로 만든다(ESLint 규칙, 검사 스크립트, CI 단계, hook). 판단이 필요한 것만 검토 기준으로 문서에 둔다. 기본은 검사 쪽 | 검토(`knol-review`)가 실수를 놓쳤을 때 |
| 항상 로드 | 항상 로드 파일(`AGENTS.md`, `kiro-harness.md`, 스킬 description)에 경로 안내가 아닌 내용이 쌓였나. 필요한 경우에만 로드되는 곳(fileMatch, auto, 스킬 references)으로 옮길 것 | 항상 로드되는 내용이 클 때 |
| 도구 비용 | 비싸거나 느린 호출(큰 출력, 긴 대기, 반복 조회)을 줄일 스크립트·옵션 | 비싼 호출을 했을 때 |
| no-op | 기본 동작과 다를 바 없는 지시문 | 지침이 길고 무거울 때 |
| 정보 접근 | 꼭 필요한 정보를 볼 수 없었나(서버 로그, 읽기 전용 외부 서비스 상태). `knol-status`에 추가할 것 | 핵심 정보가 없었을 때 |

## 3. 제안하기
심각한 순서로 보여 준다. 각 항목: 무슨 일이 있었나(세션의 근거), 무엇을 바꾸나(파일과 내용), 어떤 분류인가. Kiro 구성(`.kiro/`)은 사용자가 고르면 바로 고친다. Codex 양식(`AGENTS.md`, `.agents/skills/`)은 문안을 제안만 하고 승인을 받는다. 고친 뒤 `node .kiro/scripts/check-kiro.mjs`.

## 참고: 구현과 검토의 분업
구현 에이전트가 가장 큰 컨텍스트 압박을 받는다(탐색, 코드 작성, 실패 디버깅). 검토 에이전트는 diff만 받아 압박이 가장 작다. 그래서 코딩 기준을 지키게 하는 일은 검토 쪽 책임이고, 구현 쪽 항상 로드 지침에 기준을 쌓지 않는다.
