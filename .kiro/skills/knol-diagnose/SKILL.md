# 버그 진단

단계를 건너뛰려면 이유를 밝힌다.

## 비밀 가리기
명령·출력·캡처를 보여 줄 때 먼저 비밀을 `<REDACTED>`로 바꾼다. 쿠키·CSRF·OAuth 토큰·wrangler 자격 증명·`.env` 값. 재현 명령은 환경 변수로 자격을 받게 만든다. 진단 캡처(trace, 브라우저 저장소)에는 원고와 비공개 그림이 들어 있을 수 있으니 저장소에 커밋하지 않는다(`.gitignore`의 evidence 규칙).

## 1단계: red가 되는 재현 고리
**이것이 이 스킬의 전부다.** 이 버그에서 red가 되는 빠른 통과/실패 신호가 있으면 원인은 찾게 된다. 없으면 코드를 아무리 읽어도 안 된다. 여기에 공을 많이 들인다.

만드는 순서(대략):
1. 버그에 닿는 seam의 실패 테스트(`knol-tdd`의 `references/seams.md`).
2. 실행 중인 서버에 보내는 curl·HTTP 스크립트(로컬 서버만. 운영 도메인에 쓰기 요청은 하지 않는다).
3. fixture 입력으로 CLI 실행 후 알려진 정상 출력과 diff.
4. Playwright 단일 spec(`pnpm exec playwright test --project=host <spec>`)으로 화면을 조작해 DOM·콘솔·네트워크를 확인.
5. 실제 Ren'Py 경로(`stories-runtime` 프로젝트). 실행 묶음 변경이 있으면 `pnpm runtime:build` 다음 `pnpm build`를 먼저.
6. 실제 요청·작품 파일·이벤트 기록을 저장해 그 경로만 다시 재생.
7. 두 커밋 사이에서 생긴 회귀면 `git bisect run`으로 자동 반복.
8. 같은 입력을 이전·현재 버전(또는 두 설정)에 넣어 비교하는 차이 고리.
9. 사람이 눌러야만 재현되면(실기기·OS 파일 선택기) 사용자에게 정확한 순서를 주고 결과를 받는 반복으로 구조를 유지한다.

고리를 다듬는다: 더 빠르게(필요 없는 준비 생략, 범위 축소), 더 날카롭게(증상 자체를 단언), 더 결정적으로(시간 고정, 저장소 격리, 네트워크 고정). 간헐 버그는 깨끗한 재현보다 **재현률**을 올린다(반복·병렬·부하·대기 주입).

고리를 만들 수 없으면 멈추고 그렇게 말한다. 시도한 것을 적고 사용자에게 재현 환경, 가린 캡처, 임시 계측 허락 중 하나를 요청한다. 고리 없이 가설로 넘어가지 않는다.

완료 기준: 이미 한 번 이상 실행해 본 **명령 하나**(실행과 출력을 가려서 보여 준다)가 있고, 그 명령은
- [ ] 실제 버그 경로를 지나고 사용자가 말한 그 증상을 단언한다(red가 될 수 있다),
- [ ] 매번 같은 판정을 낸다(간헐 버그는 고정된 높은 재현률),
- [ ] 분 단위가 아니라 초 단위로 끝난다,
- [ ] 사람 없이 돌아간다.

## 2단계: 재현과 축소
고리를 돌려 red를 본다. 사용자가 말한 그 실패인지(근처의 다른 실패가 아닌지), 여러 번 재현되는지, 정확한 증상을 남겼는지 확인한다. 그다음 입력·호출·설정·단계를 하나씩 빼며 다시 돌린다. 남은 요소가 모두 필수가 될 때까지(하나라도 빼면 green이 될 때까지) 줄인다.

## 3단계: 가설
시험하기 전에 순위 붙은 가설을 3~5개 만든다. 각각 반증 가능한 예측을 단다: "X가 원인이면 Y를 바꾸면 사라지고 Z를 바꾸면 심해진다." 예측을 못 쓰면 버리거나 다듬는다. 목록을 사용자에게 보여 준다. 최근 변경이나 이미 배제한 가설을 알고 있을 때가 많다. 답이 없으면 내 순위대로 진행한다.

## 4단계: 계측
조사마다 3단계의 예측 하나에 대응시키고, 한 번에 변수 하나만 바꾼다. 우선순위: 디버거·REPL, 가설을 가르는 경계의 표적 로그. "다 찍고 grep"은 하지 않는다. 디버그 로그에는 고유 접두어(예: `[DEBUG-a4f2]`)를 붙여 나중에 한 번에 지운다. 성능 회귀는 로그보다 기준 측정이 먼저다(`performance.now()`, 프로파일러, 크기·시간 기록). 측정 후 수정.

## 5단계: 수정과 회귀 테스트
수정 전에 회귀 테스트를 쓴다. 단, 버그가 실제로 생기는 모양을 재현하는 **올바른 seam**이 있을 때만이다. 너무 얕은 seam의 테스트는 거짓 안심을 준다. 올바른 seam이 없으면 그것 자체가 발견이다. 기록하고 `/knol-retro`에서 다룬다.
1. 축소한 재현을 그 seam의 실패 테스트로 만든다.
2. 실패를 본다.
3. 고친다.
4. 통과를 본다.
5. 1단계의 원래(축소 전) 고리를 다시 돌린다.

## 6단계: 정리
끝났다고 말하기 전에:
- [ ] 원래 재현이 더는 재현되지 않는다(1단계 고리 재실행).
- [ ] 회귀 테스트가 통과한다(또는 seam이 없다는 사실을 기록했다).
- [ ] `[DEBUG-` 계측을 모두 지웠다(접두어로 검색).
- [ ] 실험용 코드를 지웠거나 표시된 위치로 옮겼다.
- [ ] 맞았던 가설을 커밋 메시지와 근거 기록에 적었다.
그다음 `disclose_context`로 `knol-verify`를 활성화한다.
