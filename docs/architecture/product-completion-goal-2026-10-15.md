# 뉴놀스토리 제품 완성 목표와 새 세션 인수인계

2026-10-29 사용자 후속 방향: [ADR0026](../decisions/0026-static-reading-authoring-and-optional-api.md)에 따라 읽기·편집의 정적 웹 독립을 우선한다. 공용 자산/런타임은 별도 CDN 전달 계층, Mac mini는 선택적 온라인 API 책임으로 좁힌다. 기존 저작·권리·로그인·기기·전체 제품 목표는 보존하며, 현재 로컬 편집 완료를 정적 공개 준비 완료로 확대하지 않는다. 실행 순서는 [단일 계획](product-completion-plan.md#정적-읽기편집-우선-순서--2026-10-29)이 소유한다.

작성: 2026-10-15. 이 문서는 사용자가 요청한 **제품 완성을 위한 다음 목표**다. 현재 편집기 안정화만 완료하고 제품 전체를 완료했다고 판단하지 않는다. 실제 구현 상태는 [STATUS](../../STATUS.md), 전체 구조와 출시 정의는 [Blueprint](development-blueprint.md)가 소유한다. 과거 계획과 검증은 당시 기록으로 보존하며 최신 사용자 결정과 현재 source를 우선한다.

## 목표

현재 로컬 개발판을 이어 뉴놀스토리에서 작품 만들기→편집→미리보기→저장→파일 왕복→재열기→읽기→공유/수업 사용까지 필요한 제품 흐름을 완성한다. 현재 편집·읽기 UI와 음원·연출의 안정화를 먼저 끝내고, 승인된 제품 범위의 서버·계정·온라인 업로드·권한·학급·과제·제출·공유 및 출시 준비로 진행한다. 미확정 운영 정책을 임의로 확정하지 않는다. 실제 출시와 기기 검증까지 완료 증거가 없다면 제품 1.0 완료를 선언하지 않는다.

## 최신 우선순위 — 2026-10-18 로컬 작품 파일 우선

2026-10-19 사용자 확정: 작품 저장의 기본은 이용자 기기의 실제 로컬 작품 파일(`.knolstory`/`.shortstory`) 저장이다. 온라인 동작은 로컬 작품을 서버에 명시적으로 **업로드**하는 기능이며 기본 저장이나 로컬 파일 저장 완료로 표현하지 않는다. 버튼·완료·재시도 안내는 업로드/다시 업로드로 통일한다. 서버 내부의 persistence·revision·DB 저장이라는 기술 용어와 이용자의 작품 저장 동작을 구분한다.

사용자는 이용자의 실제 `.knolstory`/`.shortstory` 작품 파일 저장·재열기와, Codex가 로컬 개발 계획·진행·인수인계 파일을 근거로 이어 개발하는 두 흐름을 모두 최우선으로 지정했다. 서버/DB/계정 없이 현재 작품을 파일로 보관하고 새 브라우저 환경에서 다시 열어 이어 쓸 수 있어야 한다. 브라우저 자동 저장은 보조 복구이며 실제 파일 저장과 구분해 안내한다. 파일은 독립 보관·복구 수단이지 소실 가능성을 완전히 없앤다는 보장은 아니다.

개발의 고정 진입점과 단일 실행 계획은 계속 로컬 저장소가 소유한다. 다음 재개 지점·진행 source·확인된 증거·미해결 조건을 실제 파일에 기록하고 짧은 진입 프롬프트로 이어간다. 현재 원고/미커밋 변경을 보존한다. 이미 구현한 온라인 기능은 보존하되 온라인 결합/정책·운영 작업이 로컬 파일 흐름을 선행하지 않는다. 전체 제품 목표의 서버/수업/접근성/출시 요구를 폐기하는 결정은 아니다.

## 기본 편집 범위 — 2026-10-19

기본편집은 글·배경·기존 인물이 보이는 현재 컷 중심 화면과 이전/다음 컷의 작은 이미지/글 맥락을 제공한다. 글·배경·인물·음향·연출 전용 작업 화면은 장 안 여러 컷을 동시에 살피며 쉽고 빠르게 수정할 수 있어야 한다. 각 작업에서 사용자가 다른 종류의 정보를 골라 함께 보되, 보기만으로 해당 편집을 개방하지 않는다. 기본편집·글·배경은 기본 제공, 고급 수정은 편집 설정에서 명시적으로 개방한다. 인물과 연출은 독립적이다. 편집 UI는9:16/16:9를 주 검증 기준으로 실제 가용 화면을 쓰고 페이지 전체 스크롤을 최소화한다. 세로 휴대폰 기본편집은 사용자 확정1:4:1(이전 글/현재 가로 장면+글 수정/다음 글), 태블릿은 웹과 같은 작업 구조를 따른다. 데이터·재생·파일 보존과 구체적 화면/단순 조작 기준은 [DESIGN](../../DESIGN.md#편집-작업-영역--2026-10-19-후속-설계)을 따른다.

이 요구로 기존 디자인 문서·프로젝트 스킬/지침·목업을 대조하고 필요하면 수정·재생성한다. 과거 근거는 보존하고 대체된 범위를 표시하며 실제 화면/행동과 일치하는 현재 자료를 연결한다. 디자인 자료를 갱신한 것만으로 제품 동작 완료를 판정하지 않는다.

## 문서 역할과 읽기 순서

장기 실행의 고정 입구는 [다음 세션 목표](next-session-goal-prompt.md)다. 이 파일은 **전체 목표·필수 요구·제외 범위·제품 완료 기준**을 소유하며, 매 실행의 수치나 일지를 추가하지 않는다. [제품 완성 실행 계획](product-completion-plan.md)은 단계 간 작업 ID·의존성·다음 행동·재개 지점을 소유한다. 제품 구현 상태는 [STATUS](../../STATUS.md), 세부 설계/계약/기능별 검증은 기존 소유 문서를 사용한다. 같은 사실을 여러 곳에서 독립 관리하지 않는다.

새 세션에서는 `AGENTS.md` → `STATUS.md` → [Blueprint](development-blueprint.md) → `DESIGN.md`의 필수 읽기 순서를 따른 뒤, 이 목표와 실행 계획의 **재개 지점 및 다음 준비된 작업**을 확인한다. [문서 관리](documentation-governance.md)와 해당 작업이 가리키는 source·ADR·계약·최신 증거만 읽는다. [옛 인수인계](next-session-goal-2026-10-13.md)는 결정의 근거나 누락된 배경이 필요할 때 참조하며 전체 연대기를 매번 읽지 않는다. 같은 세션에서는 이미 읽은 문서를 반복해서 통독하지 말고 변경된 부분/새 의존성만 확인한다.

현재 미커밋 변경이 개발 상태의 원본이다. Git/프로세스/빌드 상태를 확인하고 기본 브랜치 체크아웃·reset/clean·기존 작업 덮어쓰기 없이 이어간다. 다른 작업의 프로세스를 종료하지 않는다. `story-maker`는 고정 기준 `18da4fc5bd4bf2a9080b32903d31f1aacdd24a0b`를 읽는 용도로만 사용한다. 필요한 옛 내용은 현행 형식으로 명시 변환하고 원본을 보존한다.

실행 중 여부·버전·검사 수·포트·임시 스크립트 경로는 고정 목표의 상수가 아니다. 실행 계획의 재개 지점을 현재 PID/로그/코드/빌드에 대조한다. 상태 JSON의 running 표기나 과거 성공만 믿지 않는다. 살아 있는 검사는 같은 실행을 관찰하고, 끝난 검사는 증거를 회수한 뒤 영향 범위에 따라 다음 행동을 결정한다. 임시 `.cache`가 없으면 정식 환경/설정으로 필요한 부분만 복구한다.

## 장기 실행 규칙

1. 실행 계획에서 의존성이 충족된 최우선 작업을 골라 **같은 작업 ID**로 끝까지 처리한다. 완료된 로컬 단계를 반복하며 다음 서비스 단계를 미루지 않는다. 구현과 검증을 나누되 원래 사용자 흐름을 축소하지 않는다.
2. 새 작업마다 전체 감사를 다시 작성하지 않는다. 기존 세부 계획에 이어 수정하고, 작업 큐에는 해당 문서/완료 조건/증거 링크만 둔다. 대규모 목표 변경이나 모순이 확인될 때만 전체 범위를 재평가한다.
3. 검사는 변경 영향에 맞춰 좁게 시작한다. 실패를 재현→수정→동일 회귀→영향 검사 순으로 진행한다. 전체 회귀는 단계/통합/출시 후보 경계와 광범위 변경에 수행하고, 중간 focused 성공을 전체 성공으로 합산하지 않는다.
4. 통과한 검사는 관련 source·계약·입력·빌드·환경이 같고 미해결 실패가 없으면 재사용한다. 날짜나 새 세션만을 이유로 재실행하지 않는다. 반대로 변경 영향이 불명확하면 관련 범위를 넓혀 확인하며 안전을 위해 필요한 검사를 생략하지 않는다.
5. 관찰 timeout으로 검사를 재시작하지 않는다. 부분 실행을 재개할 때 남은/실패 범위를 이어가되, 전체 성공 조건이 필요한 단계에는 최종 동일 후보의 전체 실행을 별도로 남긴다. 같은 실패·같은 수정 없는 재시도를 반복하지 말고 원인/증거를 추가한다.
6. source·환경·입력·결과·증거 경로를 남긴다. 과거 증거/manifest를 덮지 않고 실행별 폴더를 사용한다. 라이브 로그를 완료 manifest로 봉인하지 않는다. 빌드/런타임 공유 자원의 변경과 브라우저 검사는 충돌하지 않게 직렬화한다.
7. 세션 끝/단계 전환에는 실행 계획의 재개 지점을 **교체 갱신**한다. 끝난 일의 연대기를 계속 덧붙이지 않는다. 다음 행동·미해결 문제·작업 소유/프로세스·후속 검사의 재실행 사유가 있으면 다음 세션이 추측 없이 이어갈 수 있다.
8. 필요한 사용자 결정은 이미 확정된 결정과 분리해 실행 계획의 질문 목록에 한 번 기록한다. 중복 질문 없이 구체적 선택지/추천/영향을 묶어 질문하고, 답변이 필요한 작업만 기다리며 다른 준비된 작업은 계속한다.

## 반드시 유지할 제품 원칙

- StoryDocument/`.knolstory`가 원본이며 Runtime Core가 Flow·배치·자산·연출·읽기 상태를 해석하고 Ren’Py가 실제 장·컷 이야기를 재생한다. Ren’Py에 StoryDocument를 전달하거나 별도 영구 Web story player를 만들지 않는다. ShortStory 읽기/A4만 Web/CSS 예외다.
- 원고·Asset ID·Flow·StageComposition·자유 배치·기획/메모·점수·갈래·읽기 경로·기존 private 자료를 보존한다. 의미가 바뀌면 검증/버전/명시 변환을 함께 구현한다. `.rpy`를 저작 파일로 삼지 않는다.
- 변경하는 계약의 현재 버전은 source와 정식 계약에서 확인한다. 세션마다 모든 버전을 전수 재검사하지 않는다. 현재 `.knolstory`·Excel·Google 시트·JSONB 의미를 연결하고 TSV 제한 표를 전체 워크북 편집과 혼동하지 않는다.
- 기존61+추가469=공용530개와 별칭23개를 유지한다. 새 음원 취득·생성은 이번 목표의 필수가 아니며 반복하지 않는다. 현재 장면별 on-demand 전달을 유지하고 새469개를 시작 ZIP에 통째로 편입하지 않는다.
- 서비스 등록 이미지/음원만 새로 선택할 수 있다. 외부 업로드를 열지 않는다. 기존 기기의 private 자료 보존/내보내기와 신규 private 첨부 거부를 구분한다. Pixabay14개는 승인된 장면 결합 사용·원음 미첨부 제한을 유지한다. 배포 권리/전달 범위는 실제 배포 환경에서 별도 확인한다.
- 현재 승인된 도안과 최신 사용자 수정을 따른다. 옛 UI를 테스트 통과 목적으로 복원하지 않는다. 테스트의 핵심 보존/취소/오류/전체 문서/native 조건을 삭제·조건부 생략하지 않는다.

## 단계 A — 제작·읽기 로컬판 안정화

현재 구현부터 대조하고 실패를 옛 경로/현재 정책에 따른 의도적 제외/실제 제품 결함으로 분류한다. 새 버튼이나 분석 문서만 추가하고 끝내지 않는다.

- 기본 편집: 현재 컷의 대사·해설, 배경·인물과 자유 배치, 짧은 이전/다음 원고와 이동, 필요할 때 여는 메모. 작은 작품/장/컷/저장 상태와 일관된 명칭을 유지하고 중복·과한 상단 공간·여백·깊은 동선을 줄인다. 겹침은 실제 열린 패널/내용 구조에 맞춰 고친다.
- 추가 편집: 연출/소리/선택지/점수를 목적별 최소 단계로 조정한다. 선택지만/점수만/둘 다/둘 다 없음의 네 경우를 검증한다. 점수 없는 작품에 빈 상세나 자동 점수를 만들지 않는다.
- 연출/소리: 대상·시작/종료 컷·적용 범위·갈래 조건·시작 시점·지속 시간·순서·반복을 한글/초 단위로 조정하고 취소·미리보기한다. 컷/장/작품 전환의 undo·draft scope와 다른 채널/자산/배치를 보존한다. 이미 구현된 기능은 사용 가능한지 확인하고 빈 기능부터 우선 구현한다.
- 읽기: 따뜻한 글 상자와 화자/대사, 편집 미리보기와 실제 Ren’Py의 일치를 유지한다. 도구 순서는 `지난기록, 저장, 불러오기, 자동, 빠른 저장, 빠른 불러오기`다. 휴대폰의 하단 글 상자와 기본 접힌 도구를 유지한다. 슬롯/자동/빠른 저장·변경 작품 확인·실제 방문 경로·되돌림·합류·엔딩·재개·동일 컷 편집 복귀를 검증한다.
- 파일/저장: 독립 사본·다중 탭·저장 실패·손상 자료·삭제/복구·지연된 파일/시트 응답·한글 조합 중 이동을 확인한다. 실제 작품을 수정해 전체 project와 자료 ID/bytes를 비교하고 파일/워크북/JSONB 및 재열기·native까지 검증한다. Excel ChatGPT 추가 기능 설치/로그인/연결은 사용자 결정으로 제외하며 다시 준비를 요청하지 않는다.
- 네 화면/입력: PC·태블릿·휴대폰 세로/가로, 긴 한국어·긴 선택지·한글 조합을 확인한다. 모의 viewport/IME 이벤트와 물리 삼성 가상 키보드·외장 키보드를 구분한다. 최초 Chrome 오류는 최초 trace 없이 해결됐다고 판단하지 않는다.

직전 집중 검증과 최근 단위 결과는 각 검증 기록에서 확인한다. 숫자를 합산해 전체 성공으로 부르지 않는다. 특히 `creative-reading-journey`, `stories-runtime`, `existing-score-runtime`, `four-work-runtime`, `authoring-format-runtime`의 native 전용 경로는 host 성공만으로 증명되지 않는다. 등록 음원을 사용해 빈 작품부터 만드는 실제 창작 여정도 유지한다. 서버가 끝날 때까지 이 단계만 반복하지 말고 완료 조건이 충족되면 다음 단계로 이동한다.

## 단계 B — 온라인 서비스의 실제 구현

[최종 구조](knolstory-final-architecture.md), 현재 `server/`·공유 validator·API/JSONB·자산 저장 계약과 기존 결정을 먼저 확인한다. 서버 구현을 이미 완료한 것으로 추정하지 않는다. 추천 PostgreSQL/Node 구성은 실제 인프라 승인과 다르다.

- 계정/인증·로그아웃·사용자/역할·소유권·권한을 구현하고 다른 사용자의 문서/자료 접근이 차단되는지 검증한다.
- 현재 저작 계약을 사용하는 온라인 작품 업로드/조회/갱신/목록/삭제/복구와 local-first 동기화를 구현한다. 충돌·revision·중복 요청·동시 편집·네트워크 단절/복귀·재시도·기기 전환에서 저작 손실을 막는다. JSONB 직렬화 테스트만으로 실제 DB 저장/복구 완료를 주장하지 않는다.
- 승인된 역할에 따른 학급/학생 참여·과제 생성/배포·제출/재제출·교사 열람을 연결한다. 제출 당시 문서/등록 자산 snapshot과 이후 편집의 관계를 명시하고 권한/시간/중복/실패 복구를 검증한다.
- 게시·공유 링크·공개/비공개·공유 취소와 접근 범위를 구현한다. 제출/공유 뷰어도 같은 Runtime Core/Ren’Py를 사용한다. per-story/student Ren’Py 패키지를 만들지 않는다.
- API/DB/파일 경계 입력 검증, 권한, 안전한 세션, 민감 정보, 요청 제한, 오류 처리와 운영 로그를 실제 구현 범위에 맞게 검증한다.

인증 제공자, 가입/학급 승인, 제출/재제출, 공유/공개, 보관/삭제 및 출시 범위는 현재 미확정일 수 있다. source/ADR에서 이미 결정된 내용은 재질문하지 않는다. 미확정이면 선택지·추천·구현 영향·검토 가능한 계약/로컬 시제품을 준비하고, 꼭 필요한 결정을 묶어 질문한다. 답을 기다리는 동안 승인된 독립 작업은 계속한다. 임의의 운영 정책이나 mock 버튼으로 서비스 완료를 대신하지 않는다.

## 단계 C — 제품 검증과 출시

- 현재 변경에 맞는 unit/integration/host/native/DPR/빌드/타입/린트를 실행한다. 코드·버전·입력·실행 범위·결과·실패/제외·실제 영상/픽셀/상태를 보존한다. 새 변경이 없으면 의미 없는 반복 검사를 피한다.
- 실제 목표 Windows/Chrome·Chromebook·Android 휴대폰/태블릿에서 로딩·성능·화면 회전·터치·표준/분할/플로팅 키보드·물리 키보드·한글 입력을 검증한다. 키보드와 스크린리더로 실제 읽기·선택을 확인한다. 대상/성능 기준은 관련 ADR을 읽고 측정한다. 하드웨어 접근이 없으면 검증 도구/절차를 준비하고 미검증으로 남긴다.
- 음원별 청취/loop/음량 및 배포 시 자산 전달·출처/권리·Pixabay 조건을 확인한다. 자동 decode/hash와 실제 청취·권리 승인을 구분한다.
- 설정/비밀값·도메인·배포 산출물·백업/복구·관찰/장애 대응·업데이트/되돌리기 절차를 준비한다. 실제 Next 자료와 DB/자산 snapshot을 복원해 읽기/편집을 확인한다.
- `story.knolquiz.com`의 승인된 출시 후보를 배포하고 실제 서비스에서 계정→작품 제작/저장→기기 전환→읽기→수업/제출/공유→복구까지 확인한다. 로컬 빌드나 배포 명령 접수만으로 완료하지 않는다.
- 외부 게시·push·배포·유료 작업·인프라/인증정보/제3자 자원 변경은 적용되는 승인 경계를 따른다. 승인 전에 가능한 구현·설정안·검증·배포 후보를 구체적으로 완성한다. 이 목표 문서 자체를 모든 외부 변경의 포괄 승인으로 해석하지 않는다.

## 우선순위와 완료 관리

진행 상태·작업 순서·의존성·작업별 완료 조건·근거·질문·다음 행동은 [단일 실행 계획](product-completion-plan.md)에서 관리한다. 세부 기능 계약·계획은 기존 소유 문서에 유지한다. STATUS에는 의미 있는 제품 상태 변화와 계획 링크만 반영하고, 모든 실행 로그를 다시 복사하지 않는다. DESIGN·계약은 실제 디자인/의미가 달라질 때 갱신한다.

현재 편집·읽기/파일 안정화 → 온라인 업로드/권한/동기화 → 학급/제출/공유 → 기기·접근성·성능·권리/복구 → 승인된 최초 출시로 진행한다. 실기기 준비/정책 결정처럼 독립 가능한 후속은 앞 단계 동안 병행한다. 표정·카메라·통합 timeline P2가 필수 서비스 완료를 밀어내지 않게 한다.

체크리스트를 쉬운 기능으로 축소하거나 검사를 생략해 완료하지 않는다. 제품 완료를 선언하기 전에 이 목표의 전체 요구와 Blueprint 완성 정의를 현재 상태/직접 증거에 항목별로 대조한다. 로컬 구현·실제 외부 앱·물리 기기·배포·정책 승인은 각각 판정한다. 재개를 위한 좁은 확인과 최종 전체 완료 감사를 혼동하지 않는다.

## 새 세션 진입

복사할 프롬프트는 [고정 진입점](next-session-goal-prompt.md)에만 둔다. 이 목표를 읽은 뒤 [실행 계획](product-completion-plan.md)의 재개 지점과 다음 준비 작업으로 이동한다. 프롬프트 문구를 여러 파일에 복제하지 않는다.
