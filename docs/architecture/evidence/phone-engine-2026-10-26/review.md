# 실제 엔진과 인접 장면 캡처의 짧은 대조

정상 캡처와 검사 harness에서만 요청을 제한한 두90초 실행을 수행했다. 각각7회 편집·1회 실제 native 복귀·원고 전체/기존 작품 보존·원래 편집 복귀를 확인했다. 최종 파일 내보내기는 이번 조사 범위가 아니다.

정상은 WASM linear capacity289,996,800bytes, 제한은201,326,592bytes였다. 정상의13개 PNG 응답은 총4,004,546문자(data URL)였다. 제한은 요청27개를 보내지 않고 응답0개다. 요청 수 차이는 응답/캐시 유무 때문에 생기며 같은 캡처량의 비용 비교가 아니다. 두 실행의 순서·초기화·캐시 상태가 완전히 같다고 증명하지 않았으므로 영향의 단서로 사용한다.

WASM buffer 용량 차이는 임시 할당의 최대점 도달 후 남은 capacity일 수 있다. live allocator 사용량·RSS·GPU·전체 프로세스 메모리가 아니며 누수나 충돌 원인을 확정하지 않는다. engine performance.memory의225,000,000은 두 경우 동일한 거친 값으로 정확한 엔진 메모리 비교에 사용하지 않는다.

모든 임시 wrapper/listener는 마지막에 원래 작품 전체 일치 확인 후 같은 페이지 새로고침으로 제거했다. 계측 전역이 없고 실제 runtime revision이 일치하며 원고가 유지됨을 확인했다. 사용자 설정·다른 탭·Android 보안/화면 설정은 바꾸지 않았다.

다음 개선 후보는 fixed1280×720 장면의 논리 구도를 보존하면서320×180 readback 전에 native Render를 축소하는 경로다. 현재 render_to_surface는 draw.screenshot 후 축소하므로 먼저 전체 크기의 surface가 생긴다. pinned SDK가 지원하는 Render/Transform 경로와 실제 이미지 동등성·활성 장면 복원을 확인한 뒤 구현한다. 제품의 인접 장면이나 단일 Ren’Py 책임 경계를 제거하지 않는다.
