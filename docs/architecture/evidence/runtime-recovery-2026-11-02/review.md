# 무대 연결 실패와 재연결 검토

2026-11-02. SD-03의 무대 오류·연결 지연 후속이다. 전체 제품 완료나 전체 캐시 검증으로 확대하지 않는다.

기존 무대는 준비가 오래 걸려도 안내만 표시했고, 오류 뒤 원고 화면을 새로고침하지 않고 실행기를 새로 준비하는 버튼이 없었다. 연결90초 또는 장면 응답15초 지연, 실행 오류·등록 음원 실패 시 무대 안에 ‘무대 다시 연결’과 ‘편집으로 돌아가기’를 제공한다. 글·현재 컷·편집 설정은 Web 상태에 그대로 둔다.

재연결은 사용자가 명시적으로 누를 때만 실패한 iframe을 교체한다. 일반 컷 이동·크기 변경·편집화면 전환의 실행 창 재사용은 유지한다. 새 WindowProxy로 이전 문서의 늦은 메시지를 거절한다. 음원 확인 목록·재생 확인·전환 확인·클릭 소모 상태를 초기화하고, IDB 대기 전후의 세대를 확인해 이전 비동기 작업이 새 음원 요청을 건드리지 않게 한다. 원고·독자 진행 저장은 삭제하지 않는다.

## 검증 경계

네트워크로 첫 index 요청을 실제 차단한 뒤 호스트의90초 대기 타이머만 짧게 실행해 안내를 열고, 재연결한 실제 Ren’Py가 현재 원고를 표시하는 검사를 추가했다. 실행 오류의 안전한 사용자 문구와 편집 복귀는 검증된 같은 출처 iframe의 계약 오류 메시지로 검사한다. 등록 음원의503→정상 재요청은 별도 실제 네트워크 검사로 구분한다. 최종 수치와 실행 결과는 [체크포인트](checkpoint.json)가 소유한다.

초기 전체 병렬 커버리지 실행은 다른 native 검사와 동시에 돌아 전체 원고 왕복3건이5초 제한을 넘었다. 데이터 단언 실패와 구분하며, 이를 통과로 기록하지 않는다. 동시 CPU 부하를 줄인 `--maxWorkers=2` 재실행 결과를 사용한다. 무관한 원고 변환 구현을 고치거나 단언을 제거하지 않는다.

고정 URL은 기존 `_headers`의 `no-cache`, 빌드 해시 파일은 immutable 정책을 유지한다. 이전 배포→새 배포를 한 브라우저 캐시에서 넘나드는 확인과 정적 전송 실패·기기/느린 망 전체 검증은 별도 후속이다.

초기 대기 검사에서 브라우저 전체 가상 시계를 사용했을 때 Ren’Py WebAssembly의 시간 기준까지 바뀌어 런타임 예외가 났다. 이 결과를 제품 재연결 실패로 단정하지 않고, 호스트의90초 타이머 하나만 단축하며 실제 실행기의 Date/performance/타이머는 그대로 둔 검사로 분리했다.

## 이전 배포에서 새 배포로 이동

[재현 스크립트](measurement/cache-release-transition.mjs)는 실제 두 불변 빌드와 제품의 production ingress를 사용한다. 같은 브라우저 origin과 기본 캐시를 유지하며, API는503으로 둔다. 이전 빌드에서 쓴 글을 임시 보관한 뒤 서버의 제공 빌드만 바꾸고 새로고침했다. 새 hash script 목록·현재 후보 파일 존재, 원고 동일성, 이전/이후 실제 Ren’Py sceneRendered, 페이지 오류0과 HTML no-cache를 확인했다. [결과](cache-transition.json). 이 실행은 Cloudflare edge의 이전 캐시를 가진 실제 브라우저를 배포 순간에 유지한 검사는 아니다. 현재 운영 edge의 파일/SHA 검증과 구분한다.

[운영 파일 검사](live-files.json)와 [신규 그림 검사](live-images.json), [같은 후보의 ingress 검사](ingress-check.json)를 완료했다. 최종 CI와 원격 브랜치는 체크포인트에서 확인한다.
